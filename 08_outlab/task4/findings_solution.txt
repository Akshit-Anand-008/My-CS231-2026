== 3. One level deeper ==
command: taskset -c 1 perf record -e L1-dcache-load-misses -c 10000 ./grid_bfs.out ; perf report --stdio --no-children --sort sym -g none
## Hint: same report command; this time the first column is the share of cache misses.
    52.92%  [.] next_pressure_value(...)
    28.15%  [.] compute_congestion_pressure(...)
    17.39%  [.] shortest_path_bfs(...)
## 81% of L1 misses are in the congestion pass. Many land in next_pressure_value although it only reads its
## arguments: on AMD the sample lands a few instructions after the load that missed (skid), here across the call.
## Reading compute_congestion_pressure: the inner loop runs over row, and index = row * cols + col, so each step
## moves cols x 4 = 1040 bytes: a new cache line for every read of current, source and next.
command: perf stat -e page-faults ./grid_bfs.out  ->  99,596 page faults
## Hint: perf stat -e page-faults ./grid_bfs.out; then look in shortest_path_bfs for new, vector or string declared inside the function.
## shortest_path_bfs calls new int[67600] and new unsigned char[67600] per request and never frees them:
## 1200 x 338 KB = 400 MB of fresh pages (kernel_init_pages, do_anonymous_page in the profile) and a memory leak.

== 4. Diagnosis ==
hotspot 1: cause = function call overhead because next_pressure_value is a real call 272 M times (4096 passes x
           258 x 258 cells), 9 arguments each, and it is 41.9% self on its own
hotspot 2: cause = stride/cache misses because the congestion loop walks down columns of a row-major array
           (L1 misses 1.06 G, 81% of them in this pass; cheap ones, the arrays fit in L2)
hotspot 3: cause = allocation because each BFS call allocates (and leaks) 338 KB: 99,596 page faults, 0.14 s sys
## Hint: the evidence is the self % row in perf report. For the leak run valgrind --leak-check=full ./grid_bfs.out --small and read the "definitely lost" line and the frames under it.
